1) WHY THE KEYCHAIN CAN NEVER BE TOUCHED IN THIS CONFIGURATION
   nsh/src/door.rs force-disables the OS keychain for debug builds AND test environments,
   on BOTH commits. The nsh-run-agent dev host is a debug build (debug_assertions on),
   and the mandated SIMCTL_CHILD_EBIR_TEST_ENV=1 makes test_environment() true — either
   condition alone suffices.

   d7fc83be (main), nsh/src/door.rs:112-116:
     fn switch_off_keychain(debug_build: bool) {
         if debug_build || test_environment() {
             // SAFETY: called from [`process`], once, before NSH or this crate starts a thread (see there).
             unsafe { std::env::set_var(bir_core::platform::NO_KEYCHAIN_ENV, "1") };
         }
     }
   (called at line 86: switch_off_keychain(cfg!(debug_assertions));)

   d6261aff (#335), nsh/src/door.rs:115-119 — identical body:
     fn switch_off_keychain(debug_build: bool) {
         if debug_build || test_environment() {
             // SAFETY: called from [`process`], once, before NSH or this crate starts a thread (see there).
             unsafe { std::env::set_var(bir_core::platform::NO_KEYCHAIN_ENV, "1") };
         }
     }
   (called at line 86, immediately before line 89 bir_core::platform::prepare_app_storage();)

   Effect per bir_submit::ios_storage::clear_on_fresh_install docs: "With the Keychain off
   (BUWIZ_NO_KEYCHAIN=1) nothing is called and no marker is written". All keyring/keychain
   reads return nothing and writes report failure without touching the OS keychain.

5) SIGN-IN PERSISTENCE FILE LIVES IN PER-PROCESS SCRATCH tmp — EVERY RELAUNCH IS SIGNED OUT
   The account file landed at tmp/ebirforms-door/<pid>-0/buwiz-cloud-account.json inside the
   data container (observed pid 84615 for the main launch) because EBIR_TEST_ENV gives every
   process a fresh scratch database in tmp and the account file sits beside the database.
   A new pid on relaunch means a new empty scratch dir, so even the file fallback cannot
   survive. Observed behavior, both commits:
   - step 2: terminate + relaunch twice on #335 — gate both times (signed out).
     (step2-relaunch1-signed-out.png, step2-relaunch2-signed-out.png)
   - step 3: uninstall + reinstall same #335 .app + launch — gate (signed out).
     (step3-signed-out.png; new data container, empty marker folder, xattr re-applied)
   - step 1 install-over of #335 on main's install — gate (signed out once), step2-signed-out.png.
   Expected "still signed in" outcomes are impossible in this configuration by construction (1).

7) THIS RUN NEVER CREATES THE DEVICE KEY
   The device key is made at first send; Queue was never pressed (no return was even created),
   so no device-key/device-id keychain items could exist regardless of the keychain switch.
   Everything measured here concerns the sign-in item (service com.buwiz.bir,
   account desktop-refresh) only.

CONCLUSION
   As configured (dev-host debug build + mandated EBIR_TEST_ENV=1), the keychain is
   force-disabled by the app itself on both commits, no keychain item is ever written,
   no install marker is ever written, and every relaunch/reinstall comes back signed out.
   The only #335 behavior observable in this configuration is the backup-exclusion xattr,
   which IS applied. Exercising the keychain paths needs a configuration the owner did not
   approve for this run (no EBIR_TEST_ENV and/or a non-debug build).
