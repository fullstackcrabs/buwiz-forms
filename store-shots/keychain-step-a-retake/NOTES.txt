            check_asked: std::env::var(KEYCHAIN_CHECK_ENV).is_ok_and(|value| value.trim() == "1"),
            ios: cfg!(target_os = "ios"),

        if (debug_build || facts.test_environment) && !keychain_used(facts) {
            // SAFETY: called from [`process`], once, before NSH or this crate starts a thread (see there).

4. Why the Keychain never came on — the evidence chain
=====================================================================
a) Not the launch env (section 2) and not the door logic (section 1 — with ios=true and check_asked=true
   the force-off cannot fire, and keychain_disabled() is re-evaluated at every operation with nothing in
   the environment or the config layer that would switch it off: dev_env.rs is Android-only,
   desktop.rs:988/1407 and door.rs:588 are desktop/test-only).
b) The dev host binary: codesign -d --entitlements on /tmp/bir-kc335.app shows NO ENTITLEMENTS at all;
   the signature is adhoc (codesign -dv: flags=0x2(adhoc), Signature=adhoc). On current iOS Simulator
   runtimes SecItem* calls from a binary with no application-identifier/keychain-access-groups
   entitlement fail (errSecMissingEntitlement class of failure).
c) That single cause explains every observation:
   - keyring_save: set(&OsKeychain, &SIGN_IN, raw) fails -> keyring_save returns false -> the caller
     discards it (cloud_account.rs line 767: let _ = keyring_save(&raw);) -> no cku row, no error anywhere.
   - clear_on_fresh_install: all three deletes fail -> FreshInstall::Incomplete -> the marker is written
     only when nothing failed (ios_storage.rs lines 197-211), so NO marker on either launch.
   - exclude_from_backup is a plain filesystem xattr call — unaffected, which is why the xattr is present.
d) Contributing observability bug in the dev host: prepare_app_storage() runs inside door::prepare_process()
   at module registration (nsh/src/lib.rs line 46), BEFORE logging is installed (install_logging runs on the
   first Door call, lib.rs line 125 / door.rs line 51). tracing has no subscriber yet when
   tracing::info!("Keychain at launch: {outcome:?}") fires (crates/bir-core/src/platform/ios.rs), so the
   line the recipe tells you to expect is DROPPED on every dev-host launch — it can never appear in
   tmp/ebirforms-logs-<pid>/logs/. Even a perfect run cannot produce the log line the check asks for.
e) The gpui-agent log line "gpui-agent listening (platform=desktop, app=bir-shell ...)" in an iOS-sim
   process is a misreported constant, unrelated but confusing.

What this run does NOT show (per the owner's standing note): the device key and device id rows — nothing
was ever sent or registered (no Queue, no device registration); and the shipped app's own access group —
this is the dev host com.longbridge.nsh.host, whose rows (had any been written) would sit in the host's
access group, not the shipped app's.
